# 卡周期 · 架构设计与小程序路线

更新：2026-07-27

## 一、架构原则

这个项目最值钱的资产不是界面，是**"周期归属和还款日怎么算"这套规则**。
所以架构的第一原则：**核心规则只写一份，谁都来复用它**。

```
                    ┌─────────────────────────┐
                    │        core.js          │
                    │  纯函数 · 零依赖 · 无界面  │
                    │ ─────────────────────── │
                    │ 日期数学  nextStmt/prevStmt│
                    │ 周期计算  calc            │
                    │ 日历生成  buildICS        │
                    └───────────┬─────────────┘
              ┌─────────────────┼─────────────────┐
              │                 │                 │
      ┌───────┴──────┐  ┌───────┴──────┐  ┌───────┴──────┐
      │  网页版 PWA   │  │  微信小程序    │  │  测试套件     │
      │  index.html  │  │ （二阶段）     │  │  test/       │
      │  localStorage │  │  wx.storage → │  │  node --test │
      │              │  │  云开发(三阶段) │  │  CI 自动跑    │
      └──────────────┘  └──────────────┘  └──────────────┘
```

**规矩（今后开发都遵守）：**

1. 任何涉及日期、周期、金额归属的逻辑，只允许写在 `core.js`。
   界面层（index.html、将来的小程序页面）只做两件事：把状态喂给 core、把 core 的结果画出来。
2. 改 `core.js` 必须先过 `npm test`（GitHub Actions 在每次 push 时自动跑，红了不发布）。
3. 存储层永远隔离在一个薄薄的适配层里（网页是 localStorage，小程序是 wx.storage，
   将来云端是 API）——换存储不动逻辑。

## 三、数据模型（两端一致）

```
people    [{id, name}]                          # 持卡人（单人模式下只有隐形的一个）
cards     [{id, personId, bank, last4,
            statementDay 1-31, buffer 提前天数, limit}]
terminals [{id, name, note}]                    # 刷卡机
txns      [{id, cardId, terminalId, date,
            amount, note, repaid, repaidDate}]  # 交易
settings  {buffer 默认提前天数, minGap 同机同卡间隔, multiUser, lastBackup}
```

单人/多人是**同一份代码的显示开关**（settings.multiUser），不是两个版本：
- 默认单人：界面完全不出现"持卡人"，卡自动归属一个隐形的"我"
- 打开多人：出现持卡人管理，卡片、流水、日历里标注人名
- 老数据（已有多个持卡人）自动进多人模式，导入备份同理

## 四、小程序路线：分三个阶段

### 阶段一（现在）：网页版就是产品
朋友用网址 + 加主屏幕。零成本、零审核、随时更新。
**这个阶段的作用是把功能打磨到位**——小程序审核一次 1-7 天，
不适合频繁试错；网页版改完 push 一分钟上线。

### 阶段二：小程序「本地版」
把网页版原样搬进小程序：core.js 直接 require，存储从 localStorage
换成 wx.setStorageSync，界面用小程序原生组件重写（WXML/WXSS）。

- **零后端、零服务器费用**——数据和网页版一样存在各自手机里
- 不需要备案域名（没有网络请求）
- 提醒改用小程序的**订阅消息**？不行——订阅消息需要后端定时下发，
  本地版做不到。替代：保留 .ics 日历导出（小程序可以用
  wx.shareFileMessage 把文件发出去），或引导用户用手机日历
- 功能上和网页版等价，收益是：微信里点开即用、朋友之间转发方便

### 阶段三：云开发「同步版」（真正的"一起用"）
接入微信云开发（云函数 + 云数据库），才能实现：

- **共享机器状态**：四台 POS 机的使用间隔基于所有人的记录计算——
  这是"一起用"的核心价值，本地版做不到
- 多设备同步、换手机不丢数据
- **订阅消息定时提醒**：云函数每天早上跑一遍所有人的周期，
  该还款的下发微信服务通知——比日历提醒更顺手
- 登录直接用微信身份（wx.login → openid），不用注册账号

**为什么选云开发而不是自建后端**：小程序的网络请求域名必须是
**已 ICP 备案的 https 域名**。你现有的 Cloudflare 域名没有备案，
走自建路线需要买国内服务器 + 域名备案（个人备案通常 2-4 周）。
云开发不受此限制（微信自己的通道），代价是绑定微信生态。

**云开发费用（如实）**：2024 年起微信云开发取消了免费额度，
基础套餐约 19.9 元/月。这是阶段三的固定成本，几个人分摊问题不大，
但值得在动手前知道。

### 数据隐私设计（三阶段都适用）

- 应用里**永远只存**：银行名、卡号后四位、账单日、金额。
  不存完整卡号、不存 CVV、不存任何能操作卡片的信息
- 云端版按 openid 隔离：每人只能读写自己的数据；
  机器使用记录只共享"哪台机器、哪天、用没用"，不共享金额和卡片明细

## 五、小程序上架流程（如实版）

### 流程本身

1. **注册**：mp.weixin.qq.com → 注册小程序 → 主体选"个人"（免费，
   需要身份证、手机号、一个没注册过公众号/小程序的邮箱）
2. **拿 AppID**：注册完成后在"设置-账号信息"里
3. **装开发工具**：微信开发者工具（macOS 版），导入项目填 AppID
4. **开发调试**：工具里有模拟器，真机用"预览"扫码
5. **提审**：工具里"上传"→ 后台"版本管理"→ 提交审核，
   填类目、功能描述、测试账号说明
6. **审核**：首次一般 1-7 天。驳回会给理由，改完可再提
7. **发布**：审核通过后手动发布，用户即可搜到

### 三个现实门槛（重要，先想清楚再投入）

**门槛一：类目。** 个人主体可选的类目有限（工具、生活服务的部分子类等）。
"信用卡管理"在微信的语境里容易被判定为**金融信息服务**，
那需要企业主体 + 金融相关资质，个人主体给不出。
现实做法是以"效率-记账/提醒"类工具提审，功能如实描述为
"记录消费、提醒还款日"。**能否通过取决于审核员的判定，
个人主体做卡片管理类工具被驳回是常见情况**——要有心理预期，
不建议为了过审在名称和描述里伪装功能，违规被发现会封号。

**门槛二：主体。** 如果个人主体走不通，出路是企业主体
（需要营业执照；个体工商户也行）。注册公司/个体户本身
是另一套流程和成本。

**门槛三：审核对内容的敏感性。** 这个工具的完整功能
（POS 终端轮换管理）在审核视角下比单纯记账更敏感。
阶段二提审时建议只带核心功能（卡片周期 + 记账 + 提醒），
机器管理可以后续版本再说——不是隐瞒，而是最小化首审面积，
这在小程序开发里是常规做法。

### 我的建议

网页版已经解决了"能用"的问题。小程序值得做，但**先去把账号注册了、
类目试提一次水**（提审不花钱，驳回不留案底），确认个人主体这条路
通不通，再投入界面重写的工夫。如果你注册好了 AppID 和开发者工具，
下一步我们就把阶段二的小程序做出来。

### 2.1 开发环境备忘

- 开发者工具是 **Electron 新版（2.02+）**，配置目录 `~/Library/Application Support/微信开发者工具/<hash>/`；
  CLI 在 `/Applications/wechatwebdevtools.app/Contents/MacOS/cli`
- 服务端口设置存于 `<hash>/WeappLocalData/localstorage_b72da75d….json`
  （`reduxPersist:settings` → `security.enableServicePort`），CLI 报"服务端口已关闭"时可直接改此文件后重启工具
- `project.config.json` 的 `libVersion` 必须是有效版本或 `latest`——
  无效版本会导致模拟器基础库加载失败与 preview 上传报 `41002 appid missing`（报错信息有误导性）
- 新版工具对 miniprogram-automator 自动化桥暂不响应（命令超时），
  运行时验证以 `cli preview`（编译+上传链路）+ 真机预览为准
- 生成预览二维码：`cli preview --project <miniprogram绝对路径> --qr-format image --qr-output <路径>`（二维码约 25 分钟有效）
- 小程序端修改 core.js 后务必 `npm run sync-core`（CI 的 check-sync 会拦不一致）
