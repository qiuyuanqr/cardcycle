## 批次 1 结论（core.js + 测试 + CI）

**验证基线**：`npm test` 30 项全过、`check-sync` 两份 core.js 逐字节一致。
逐项复核过的关键实现（均正确）：`nextStmt/prevStmt` 短月/闰年/跨年落点（测试有
31 账单日 × 800 天全扫描）；`calc` 还款冲抵的分单位整数运算；`utf8Len` 对
lone surrogate 与 TextEncoder 行为一致；`icsFold` 73 字节上限 + 续行空格后 ≤75
字节合规；`VALARM` 触发换算（全天事件 `-P2DT15H` = 3 天前上午 9 点）；
`pruneOrphans` 空卡安全阀；`buildReminders` 过期还款提醒顺延（测试中建设银行
一组恰好覆盖顺延路径）。**未发现 P0/P1。**

### P2-1 未来周期的消费会无提示吞掉还款额度

`calc` 的冲抵循环扫描该卡**全部**消费（按日期升序），归属未来周期的消费
（`k > aKey`）同样参与吃掉 credit，但既不计入 `cur` 也不计入 `over`，
返回值里没有任何字段反映它的存在。

实测复现（2026-08-02，脚本运行验证）：账单日 5 号、ref 7/27，本期 7/10 消费
50，另有一笔日期误录为 **2027-01-01** 的消费 100，随后还款 100：

```
有未来消费:  cur=0  over=0  deposit=0   label=已还清
无未来消费:  cur=0  over=0  deposit=50  label=已还清
```

- **影响**：日期手滑录成未来（典型是年份写错）时，50 元存款"消失"，概览上
  完全看不到原因，只有翻流水才能发现那笔未来消费。总账守恒（不算错钱），
  但显示与用户预期不符且零提示，排查成本高。
- **建议**（列入下一修复批次）：`calc` 返回值增加未来周期消费的笔数与金额
  （如 `futN`/`fut`），两端界面在 `futN > 0` 时明示；或在记账入口对
  「日期晚于本周期账单日」的输入加确认。修复须带测试固化。

### 备注（不构成缺陷，择机处理）

- **N1 空值兜底不一致**：`calc` 对 `payments` 有 `|| []` 兜底而 `txns` 没有；

- **N2 `money()` 边界**：负数且舍入到 0 时显示 `-0.00`（实测）。正常路径金额

## 批次 2 结论（网页版 index.html + sw.js）

**未发现 P0/P1。** 数据安全三件套（读失败拦截写入、导入/清空作为恢复路径解除
拦截、备份提醒）与 2.3 备忘一致；用户输入（银行名/商户名/备注/持卡人名）
插入 HTML 前均经 `esc()`；`histFilter` 指向已删卡时回落「全部」。

### P2-2 读失败后网页版仍可导出空备份

`load()` 失败置 `loadFailed` 后，`save()` 会拦截写入，但 `openExport` /
`copyExp` / `dlJSON` 都没有这道检查——此时 `S` 是空的 `DEF`，导出的「备份」
体积、格式看着都正常，实际是空壳，用户若拿它覆盖之前存好的备份即真丢数据。
**小程序端（`exportJSON`/`exportFile`）有此拦截，网页版漏了**，两端不一致。
建议：导出入口补同样的 `loadFailed` 检查。

### P2-3 Service Worker 会把 404/500 响应写进缓存

`sw.js` 两条路径（网络优先/缓存优先）`cache.put` 前都不检查 `res.ok`。
部署间隙或 Pages 故障返回错误页时，会用错误页覆盖缓存里的好版本，
之后断网打开 PWA 显示的就是错误页。建议：`res.ok` 才写缓存。

### 备注

- **W-a 备份导入未做字段级校验**：`normalize` 只保证五个字段是数组，不校验
  元素内部；`date`/`statementDay` 等字段未经 `esc` 直接拼进 HTML，构造过的
  备份文字可造成自 XSS（需用户自己粘贴恶意备份，风险有限）。可在 normalize
  里做字段类型清洗一并解决。
- **W-b 存储整体不可用时启动中断**：`localStorage.getItem` 抛异常的场景
  （如浏览器禁用存储），`load()` 已兜住，但启动尾部的首次种子判断
  （`if(!localStorage.getItem(KEY))`）未包 try，会中断脚本导致整页空白。
- **W-c** `wipe()` 确认文案列了卡/商户/消费数，未提还款笔数（两端同）。
- **W-d** 全局默认提前天数输入上限 10、单卡编辑上限 15，两处不一致（两端同）。
  **→ 已解决（2026-08-03，1.0.16）**：两端全局上限统一为 15；同批为参数输入补了
  保存反馈（toast 说明存了什么）、清空/乱填不再静默存成 0（恢复原值不写盘）、
  超上限按上限保存并说明；小程序端参数路径顺带检查 `save()` 返回值并回滚
  （M-a 在该路径上收敛，其余次要路径维持原样）。

## 批次 3 结论（小程序页面层 + 与网页行为一致性）

**未发现 P0/P1。** 资金计算全部走 core；三条主写路径（记消费 `saveTx` /
登记还款 `applyRepay` / 保存卡片 `saveCard`）save 失败均回滚内存并如实报错，
与 2.3 备忘一致。逐项核对与网页一致的行为：记消费的未来日期确认、
流水筛选记 id 不记下标（删卡回落「全部」）、导入走 normalize、
导出备份挡 readFailed（此项反超网页版，见 P2-2）。

### P2-4 「0 被 `||` 吞掉」在小程序端仍有两处漏网

与 2.3 已修的「提前天数 0 生效」同根因（`bufOf` 注释明说不能用 `||` 判空），
`settings.js` 改对了（`== null`），但：

- `pages/pos/pos.js:12` `S.settings.minGap || 7`——间隔设为 0 时，商户页
  红绿灯仍按 7 天判断；**网页版对应处用 `== null`，行为正确，两端不一致**；
- `pages/card/card.js:27` `S.settings.buffer || 3`——全局默认提前天数设 0 时，
  新增卡表单预填 3（网页版 `openCard` 用 `== null`，正确）。

只影响展示与预填、不碰金额，定 P2。建议两处改 `== null` 判空。

### 备注

- **M-a 次要写路径不检查 save() 返回值**：加/删商户、参数与排序调整、
  删单条流水、删卡等路径 `store.save(S)` 后不看结果；写失败时界面短暂显示
  成功，但各页 onShow 都会重新 `load()`，下次进入即自我纠正。2.3 有意只给
  三大主路径做回滚，维持现状可接受。
