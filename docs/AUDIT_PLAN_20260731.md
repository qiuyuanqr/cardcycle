### P2-1 未来周期的消费会无提示吞掉还款额度

`calc` 的冲抵循环扫描该卡**全部**消费（按日期升序），归属未来周期的消费
（`k > aKey`）同样参与吃掉 credit，但既不计入 `cur` 也不计入 `over`，
返回值里没有任何字段反映它的存在。

实测复现（2026-08-02，脚本运行验证）：账单日 5 号、ref 7/27，本期 7/10 消费
50，另有一笔日期误录为 **2027-01-01** 的消费 100，随后还款 100：

```
有未来消费:  cur=0  over=0  deposit=0   label=已还清
无未来消费:  cur=0  over=0  deposit=50  label=已还清
```

- **影响**：日期手滑录成未来（典型是年份写错）时，50 元存款"消失"，概览上
  完全看不到原因，只有翻流水才能发现那笔未来消费。总账守恒（不算错钱），
  但显示与用户预期不符且零提示，排查成本高。
- **建议**（列入下一修复批次）：`calc` 返回值增加未来周期消费的笔数与金额
  （如 `futN`/`fut`），两端界面在 `futN > 0` 时明示；或在记账入口对
  「日期晚于本周期账单日」的输入加确认。修复须带测试固化。

### P2-2 读失败后网页版仍可导出空备份

`load()` 失败置 `loadFailed` 后，`save()` 会拦截写入，但 `openExport` /
`copyExp` / `dlJSON` 都没有这道检查——此时 `S` 是空的 `DEF`，导出的「备份」
体积、格式看着都正常，实际是空壳，用户若拿它覆盖之前存好的备份即真丢数据。
**小程序端（`exportJSON`/`exportFile`）有此拦截，网页版漏了**，两端不一致。
建议：导出入口补同样的 `loadFailed` 检查。

### P2-3 Service Worker 会把 404/500 响应写进缓存

`sw.js` 两条路径（网络优先/缓存优先）`cache.put` 前都不检查 `res.ok`。
部署间隙或 Pages 故障返回错误页时，会用错误页覆盖缓存里的好版本，
之后断网打开 PWA 显示的就是错误页。建议：`res.ok` 才写缓存。

### W-b 复盘：真正的根因是 TDZ，且定级应为 P1（2026-08-07）

外部复审（Codex）报了一个可稳定复现的问题：**本机数据损坏或读不出来时，
数据确实不会被覆盖，但网页直接起不来，用户也进不了备份恢复路径。**
按本文档 W-b 的描述去查会查错地方——W-b 说断点在启动尾部的种子判断（`index.html:909`），
**实际断点比那早得多，在 `let S=load()` 那一行。**

**根因：暂时性死区（TDZ）。** 当时的代码顺序是

```
let S=load();            // 233 行：调用 load()（函数声明会提升，所以调得到）
...
let loadFailed=false;    // 255 行：let 声明，此刻 233 行还处在它的 TDZ 内
function load(){ try{ ... }catch(e){ loadFailed=true; ... } }
```

正常路径不进 `catch`，永远碰不到 `loadFailed`，所以这个雷埋了很久没响。
**但任何异常路径**——`getItem` 抛异常（存储被禁用）**或** `JSON.parse` 失败（备份/存储内容损坏）——
都会执行 `loadFailed=true`，此时 `loadFailed` 仍在 TDZ，抛
`ReferenceError: Cannot access 'loadFailed' before initialization`。
该异常从 `load()` 抛出，`let S=load()` 处无人接，**整个 `<script>` 从第 233 行中断**。

**后果（浏览器实测，两个场景表现完全一致）**：`S` 永远未定义；tabBar 的 `onclick` 绑定在
第 899 行、从未执行；`renderAll()` 从未执行。页面停在静态外壳——顶栏、加号、四个 tab 都画出来了，
**但一个都点不动**，内容区全空。用户看到的就是「应用坏了」，且**没有任何入口能走到
「设置 → 粘贴/导入」把备份恢复回来**。数据本身没丢也没被覆盖，但用户拿不回来。

**为什么当时定成备注级**：W-b 只看到了第 909 行那处裸 `getItem`，
默认「`load()` 已兜住」，没有验证异常路径下 `load()` 自己会不会抛。
**教训：认定某段代码「已经兜住了」时，要真的让它失败一次看看，不能只看有没有 try。**

**修法（三处，都在 `index.html`）**：

| # | 改动 | 治什么 |
|---|---|---|
| 1 | `let loadFailed` 提到 `let S=load()` **之前**声明 | 根因。消除 TDZ，两个失败场景都不再中断脚本 |
| 2 | 新增 `let firstRun`，由 `load()` 在真·首次打开时置位；启动尾部的种子判断改用它，**不再重读 `localStorage`** | 原 W-b 描述的那处。修好 #1 后脚本会跑到这里，存储不可用时会在这儿抛第二次 |
| 3 | 启动尾部 `if(loadFailed) alert(...)` 告知「数据没被覆盖、先刷新、别重录、别覆盖旧备份」 | 读失败时界面是空的，和「数据丢了」长得一模一样。**小程序端本来就有读失败 toast，网页版缺这一条**，属两端不一致 |

**验证（浏览器实测四场景，注入 localStorage 替身，`index.html`/`core.js` 原样加载）**：

| 场景 | 未捕获异常 | 启动写盘 | 提示 | 恢复路径 |
|---|---|---|---|---|
| A 存储整体不可读（`getItem` 抛 SecurityError） | 0 | 0 | ✅ | ✅ 能进设置页，导入弹窗可开，导出仍被 `exportBlocked` 拦 |
| B 数据损坏（截断的 JSON） | 0 | 0 | ✅ | ✅ |
| C 真·首次打开（对照） | 0 | 1（种下持卡人+商户，正确） | 无（正确） | — |
| D 正常有数据（对照） | 0 | 0 | 无（正确） | 待还金额计算正确 |

修复前 A、B 两场景均稳定复现 `Cannot access 'loadFailed' before initialization`，
点 tab 无任何反应。`npm test` 31 项在修复前后均全过（这个缺陷在 `index.html` 内联脚本里，
现有测试套件覆盖不到——**这是已知的测试缺口**，网页版的存储适配层没有自动化测试）。

**小程序端不受影响**：`store.js` 的 `readFailed` 是挂在状态对象上的属性而非模块级 `let`，
且 `load()` 由页面调用、不在模块初始化期，没有同类 TDZ 风险。

### P2-4 「0 被 `||` 吞掉」在小程序端仍有两处漏网

`settings.js` 改对了（`== null`），但：

- `pages/pos/pos.js:12` `S.settings.minGap || 7`——间隔设为 0 时，商户页
  红绿灯仍按 7 天判断；**网页版对应处用 `== null`，行为正确，两端不一致**；
- `pages/card/card.js:27` `S.settings.buffer || 3`——全局默认提前天数设 0 时，
  新增卡表单预填 3（网页版 `openCard` 用 `== null`，正确）。

只影响展示与预填、不碰金额，定 P2。建议两处改 `== null` 判空。
